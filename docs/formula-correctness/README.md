## 0. テストの有効性と最小十分性（渡辺さん 2026-10-31）

効果の薄い・目的のはっきりしないテストは作らない。件数やカバレッジを増やすことを目的にせず、数学的・機能的に重い誤りを効率よく見つけるために設計する。要るテストを省かないことと、要らないテストを増やさないことを両立する。

1. **リスクから始める**：起きやすさと影響の大きい誤りから順にテストを置く。
2. **最小十分**：同じ故障を見つけるテストを重ねない。既存のテストで見つかる故障には新しく足さず「既存で足りる」と書く。
3. **独立**：期待値と実際の値が同じ誤りを共有しない（同じ式・同じ写し・同じ計算から両方を作らない）。だから独立な見本（オラクル）を別の実装で作る。
4. **見つける力を実証する**：大事なテストは、わざと誤りを入れて止まることを確かめる（test-plan.md の M1〜M9）。
5. **整理し続ける**：見つける価値が下がったテストは統合・削除・置き換える（候補は test-plan.md の 4。消すのは統合の段で決める）。

テスト1つごとに **検証対象・想定する故障・検出方法・既存テストとの差分・リスク（起きやすさ×影響）** を書く。測るのは件数ではなく、重い故障を見つける力・まだ確かめていないリスク・実行の時間・保守の手間。classification.md の性質ごとのテストの選択規則も、この原則で絞る。

この設計で変えないもの：knowledge-net・math-lab、共有の型（docs/knowledge-net/schema とその元）、式の原本（content/terms.yaml など）、build/ の動き、CI で走るテスト、.github/workflows、tools/test_labs.js（#135 が変えている）、P5 の画面。

## 2. 共通のデータの契約（案。フェーズ0で3件が合意するまで実装しない）

### 2.1 式 ID

今の型（kn-schema 改訂11）では、式（`formulas[]`）に ID がない。今あるものは並びの番号で式を指している：

- math-lab の見本 test/fixtures/stats2-formulas.json：`{concept, index}`
- 教材の `workspace.formula`・`workspace.mean`（build/network.py）、実験室の理由の段 `reason.formula`：番号

**案**：
1. 当面（フェーズ0の合意まで）の呼び方は `<概念ID>#<番号>`（例 `TERM-binom#0`）。ネットワークでは `stats2:TERM-binom#0`。この文書群と試作の見本はこれで書く。
2. 正式には、式に任意の `id`（例 `F-binom-pmf`）を足す（型の改訂。任意の項目なので v1 のまま）。理由：番号は式を並べ替えると別の式を指す。ID は変えない・消さない（問題の ID と同じ決まり。要らなくなった式は `retired`）。
3. `id` を足すまでは、build が「番号 → 式の tex の先頭」の対応を検証の結果に書いておき、並べ替えで食い違ったら検証の結果を無効にする。

**同じ式が2か所にある**：`TERM-rv#1` と `TERM-dist#0` はどちらも Σ p(x)＝1。式の原本は1つの決まりに合わせ、片方をもう片方への参照にするか、同じ式として1つの ID を共有するかを決める（決めること D2）。

### 2.2 検証の結果と式 ID の対応

検証の結果は「式 ID × 確かめたこと」の表にする。確かめたことの名前は classification.md の性質の名前と、test-plan.md の共通テストの名前（C1〜C6）だけを使う。

```text
式ID           確かめたこと   層  方法        結果   出所（テスト名・見本の id）             式の版
TERM-binom#0   正規化         1   性質        通過   correctness.test.ts「二項分布：Σ P＝1…」  tex の先頭 / 版
TERM-binom#0   正規化         1   見本        通過   reference.json binom-n10-p3_10
TERM-binom#0   レビュー：条件  —   個別レビュー 未完了 —
```

- 結果は「通過・失敗・未検証・該当しない」の4つ。**種類か性質が未分類の式は「検証済み」にしない**（#118 の決まり）。
- 「式の版」は概念の `version` と式の内容（tree の正規化した JSON）の hash。式を直すと hash が変わり、その式の結果は未検証に戻る。
- 結果の表は生成物（out/ の下）。原本には入れない（コミットしない）。公開の JSON には、画面に出す「未検証の印」に要る状態だけを出す（D4）。

### 2.3 置き場所（案）

| 何を | どこに（案） | 理由 |
| --- | --- | --- |
| 種類・性質 | 式の原本の横（content/terms.yaml の `formulas[]` に任意の `kinds`・`properties`）か、別の原本 content/formula-contracts.yaml（式 ID をキー） | 式の原本は1つ。別のファイルにすると terms.yaml を触らずに始められるが、式を直したときに直し忘れる |
| 成り立つ条件 | **新しく書かない**。記号の `domain`（#109）と概念の `conditions.math` を参照する。記号どうしの条件（k ≦ M・a＜b など、今の domain で書けないもの）だけを足す | 同じことを2か所に書かない |
| 式ごとの検証の契約 | content/formula-contracts.yaml（式 ID・種類・性質・参照する条件・共通テスト・性質のテスト・レビューの要否・根拠） | 契約は原本（人が決める）。テストの自動選択はこれを読む |
| 個別レビューの記録 | content/formula-reviews.yaml（対象の式 ID と式の版・観点・根拠・判断・担当・日付） | 式の版が変わったらレビューは「やり直し」になる |
| 独立な見本 | stats2-course の build が書き出し（今は research/oracle/ の試作）、math-lab の test/fixtures/ に写す | #118 の「層1の独立な見本は stats2 の build で書き出し、math-lab のテストで読む」 |
| 検証の結果 | out/verify/（生成物） | 原本に結果を書かない |

どの案でも、型（kn-schema）を変えるのは「画面に出すもの」（成り立つ条件・未検証の印・式の id）だけにし、契約やレビューの記録は教材の中で持つ（knowledge-net は他の教材でも使う土台なので、検証の運用まで型に入れない）。

### 2.4 既存の of・domain をそのまま参照できるか

結論：**そのまま参照できる。作り直さない。** 足りないのは次の2つで、どちらも既存の型への任意の追加で済む（詳しくは inventory.md の 4）。
- 記号どうしの条件のうち、1つの端で書けないもの（超幾何の k ≦ M・n ≦ N、一様の a＜b、幾何の p＞0）。
- 開いた式の前提（元の式と定義の式の前提を合わせたもの）は、データではなく engine の計算で作る（まだない）。
